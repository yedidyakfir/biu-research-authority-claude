# Durable phase notices

When Configuration enables `milestone_notices.mode = durable_v1`, this is the scheduled notice path. It supersedes generic deadline/closing alert and legacy `reminder_days` assumptions for notifications. Source verification, deadline facts in the report, cadence checks, sender/recipient guards, existing digest schedule and HTML templates remain unchanged. Never send an additional or test email.

## One pair per eligible phase, not per round

Each canonical application round has separate `announcement`, `publication` and `opening` milestones, matching the existing Round fields Announcement, Publication and Opening. Anticipated publication/call-for-applications and application opening are independent dates. Each eligible dated phase/version has **discovery** (next scheduled digest) and **approaching** (default seven days before that phase). There is no two-notice maximum across a round. No deadline, closing, final-deadline or optional-question date enters this ledger.

Read the three `notice:<stage>` rows from the same native Settings database as cadence, through the configured notice settings view. Reminder days are independently editable integers 0–90; Catch-up days are independently editable integers 0–30, default seven. The existing cadence view returns only its original four rows. Do not edit the digest's Sun–Thu 08:00 Asia/Jerusalem schedule.

An eligible date is either source-verified, or a full date explicitly announced by an authoritative source with `certainty: forecast`, `officially_announced: true`, `source_verified: true`. Preserve source, verification timestamp, original timezone and the anticipated-date label. A month estimate, imported forecast, unknown cycle, guessed date or failed retrieval cannot establish a notice. A date crossing never proves publication or application availability. Unknown BIU eligibility/internal requirements remain caveats; only the existing helper's confirmed exclusion for this exact call/cycle suppresses eligible notices. Individual restrictions or lead-only restrictions do not imply blanket exclusion.

## Observation and durable persistence

Use `scripts/notice_contract.py input.json --output output.json`; every operation is no-send and creates its output exclusively. Read current native schema first. Keep private snapshots outside Git and remove them after durable read-back.

1. After a successful authoritative observation, before committing monitoring progress, call `operation: ingest` with the canonical `round_state`, its current/active notice records, a partial `observation` (`round_key`, aware `observed_at`, `source_success: true`, `milestones`, optionally current eligibility `review`), fresh `settings`, and Configuration `activated_at`. Retain the existing `notice_checkpoint`; do not reconstruct its revision counters from dates. Explicit null/unknown facts withdraw a phase; an omitted phase is unchanged. Pass failed retrievals as `source_success: false`; they establish no new date. Never pass deadline fields as notice milestones.
2. `ingest` returns a per-stage monotone date-version checkpoint and notice upserts. A repeated observation does not create another version; A→B→A creates a third version. Older observations are ignored; conflicting equal-time dates require reconciliation. Pending old versions become superseded. Existing intent/uncertain versions stay unresolved until Sent reconciliation, even after a date changes or expires.
3. Reconcile exact keys through the dedicated key lookup view before creating any native notice. Set its exact Key filter under the existing single-host lock, query the saved view, and check all matches. Use the round lookup view for active/current records; retrieve exact current-version terminal keys too when reconfirming a checkpoint, so delivered/baseline rows cannot be recreated. An empty lookup is evidence only when `has_more` is false. Never use the exhausted SQL/rows path or enumerate all history nightly.
4. Use `project` with `round_state`, `notices`, `settings`, `settings_pages` to get native property upserts. Persist pending notices first, then the Round checkpoint; read both back before advancing the source cursor. A crash between writes is reconciled by deterministic keys and the saved observation, never a second date version. Round Notice checkpoint and notice Payload are small versioned UTF-8 JSON encodings to survive Notion rich-text URL rewriting; the dates, stage, state, kind, source and relations remain readable native fields. Decode with the helper, and reject native Key/State disagreement. Keep full source/history on bounded native pages, not in these machine fields.
5. A confirmed exclusion may suppress pending notices without claiming delivery. A later evidenced correction can re-enable an undelivered current version; new rounds never inherit exclusion. Preserve terminal history and every actual receipt. The new ledger does not rewrite previous Runs, source reviews or delivery observations.

## Scheduled selection, including missed days

Run this calendar/notice path every scheduled invocation, independently of which sources are selected. First reconcile the configured unresolved-delivery view (`intent` or `uncertain`, samples excluded) against Runs and Gmail Sent. Read up to20 rows; if more remain, report unresolved delivery and do not send until reconciled. An unresolved old run remains a blocker even after its milestone expires. A send timeout is not proof of failure.

Read the pending discovery view plus one approaching view for each of the three phases. Start with up to20 rows per view; recycle unused allowance up to100 total notice rows, counting duplicates and reads used to find items. Persist separate notice view continuations and fair traversal; never reset the source cursor. All notice work shares the existing 400 metadata-row /100 connector-read bounds, and source/request/time caps; reserve space before source work. Stop and audit deferred work when any bound is reached. Do not claim every pending notice was examined if pagination remains. Current Round checkpoints for selected pending notices are metadata reads, not new source checks.

Reserve room for notices created by this run's observations, then call `select` at final digest composition on the merged pending/upsert set. Thus a date discovered during today's source checks can appear in today's next digest. Pass pending `notices` (or `native_rows`), current `rounds` keyed by canonical key, fresh `settings`/`settings_rows`, aware `now`, `unresolved_checked`, `unresolved_count`, and bounded scan/line limits (defaults100 rows/30 lines). Count all examined rows across passes if re-planning is necessary; do not reset the per-run allowance. Recompute due/expiry from current settings; do not rely solely on cached Due. The four pending views are intentionally not filtered on cached Due, so changing reminder days works immediately. Persist returned superseded/suppressed/expired states and audit any missing Round checkpoint; unselected notices remain pending.

Discovery becomes due when first observed; approaching becomes due on the phase date minus its configured days. The next existing scheduled digest catches either up through the end of the phase's local day plus Catch-up days. After that bounded window, an unsent notice expires. Weekend/missed-run notices can therefore arrive shortly after the milestone, explicitly labeled as catch-up. Do not invent a new timer or an extra email. If both kinds are due together, one compact line carries both ledger keys. Different phases and parallel rounds remain distinct.

## Exact digest intent and receipt

Use `operation: prepare` with the plan, current notice records and **fresh current Round checkpoints**, existing structured report, current verified Configuration/workspace/sender, report day, delivery state and now. This operation composes compact plain-text notice lines into existing report rows (or labeled pending rows), then calls the unchanged `pilot.prepare_email` and deterministic renderer. No model HTML step or visual redesign. Matching uses canonical `round_key`; ambiguous matches fail. Detailed ledger/search failures remain Notion-only. A pending notice can appear even when its source was not checked today, without claiming an open call or new verification.

The operation rejects superseded/excluded notices immediately before preparation, then returns the exact report, prepared email, notice states and delivery intent. Persist/read back **all** of them before the existing authorized Gmail send. Store intent on the existing Run, including notice keys, exact subject/sender/recipient list and SHA-256 of the prepared HTML. Any partial or uncertain persistence leaves a recoverable intent; do not send until reconciled. If a current phase changes before sending, regenerate the digest; never send a stale plan.

After sending, call `reconcile` with the saved intent, notice records and actual Gmail Sent read-back: message ID, aware sent time, SENT label, exact sender/To, empty Cc/Bcc, exact subject and SHA-256 of the decoded HTML body, plus `verified_from_sent: true`. Only this result marks ledger rows delivered. One line containing both kinds delivers both keys. Persist/read back the Run receipt and each notice receipt idempotently. A historical version can receive its actual receipt after a newer version exists; that never marks the newer version delivered.

On uncertainty, record `kind: uncertain` and connector evidence; reconcile Sent before any retry, across date keys. Only explicit proof the connector did not accept the send permits `definitive_not_sent`, restoring pending notices for the next eligible digest. Never reset a confirmed receipt. Existing run-level idempotency still applies, including a digest with no notice rows.

## Initial baseline and rollback

Initialize existing rounds once from saved authoritative facts, with `baseline: true` and the saved activation timestamp. Suppress historical discovery, and suppress approaching notices for dates already before activation's local day. Preserve a future phase's approaching reminder; this is not a claim of new discovery. Unchanged baseline versions stay suppressed. New post-activation observations create normal notices, while explicit historical imports stay baseline-only. Leave unknown phase dates unknown; do not infer publication dates from observation times.

Rollback disables/removes only `milestone_notices` from Configuration and reverts the focused code commits if needed. Keep additive ledger/checkpoints/history for inspection. Preserve existing cadence fields, legacy data, delivery receipts and schedule. Safe schema samples have `Sample=true`, suppressed state, synthetic identities and no live Round/Run relations; all delivery queries and helpers exclude them.
